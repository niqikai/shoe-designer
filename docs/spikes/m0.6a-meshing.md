# M0.6a 网格提取方案评估：OpenVDB / manifold3d

评估对象是实现计划 M0.6a 里的两个现成方案，看它们能否代替 M0.6 自写的 numba Marching Cubes（ADR 0005）。只做评估，不接入主代码；脚本在 `spikes/m0_6a/`，大的中间结果在 `.scratch/m0_6a/`（已被 gitignore）。

## 结论

**两个候选都不能同时满足 5 项硬性条件，按判定规则回退到 M0.6 原方案：自写 numba Marching Cubes + 全局边编号焊接。M0.6 的模型和强度不变（O·xhigh）。**

| 候选 | 安装 | 正确性 | 跨块 | 确定性 | 授权 | 结论 |
|---|---|---|---|---|---|---|
| A. OpenVDB `volumeToMesh` | **不通过** | 未评估 | 未评估 | 未评估 | MPL-2.0（Homebrew 元数据） | 不通过：安装 |
| B. manifold3d `Manifold.level_set` | 通过 | 通过 | **不通过** | 通过 | Apache-2.0 | 不通过：跨块 |

B 失败的原因有两条，都是实测得到的：

1. **一次提取整个包围盒**：`level_set` 对包围盒内每个网格点回调一次，时间和内存跟包围盒体积成正比，跟表面积无关。鞋子大小的盒子（300 × 120 × 150 mm）里只放一个 R = 20 mm 的球，edgeLength 0.25 mm 就要 77.5 s、峰值 RSS 4.28 GB，而同一栅格的 float32 稠密数组只有 1.29 GB。这正是 ADR 0005 拒绝的“整鞋稠密栅格”问题，而且更糟。
2. **分块提取再拼接**：每次调用都会在包围盒边界上补一层盖子，所以相邻块不能直接焊接。加重叠区再按三角形归属裁剪后，体素是 2 的整数次幂分数（1.0、0.25 mm）时，拼接结果与单次提取逐位相同；体素不是这类数（0.3 mm）时，同一个顶点在两次调用里相差约 3e-14 mm，不能按精确坐标焊接，出现 372 条开放边。体素大小由 profile 决定，不能限定成 2 的幂。

另外 B 有两个与硬性条件无关、但 M0.6 需要知道的事实：RSS 看门狗线程在 `level_set` 期间被饿死（见第 6 节），以及 manifold3d 在内存上的运行间波动很大。

## 测试环境

- macOS arm64（Darwin 27.0.0），10 核，16 GB；Python 3.11.17；uv 0.13.1。
- numpy 2.4.6，numba 0.68.0，manifold3d 3.5.4（项目 `uv.lock` 里已有），scikit-image 0.26.0（只作速度参照，`uv run --with` 临时安装，没有改 `pyproject.toml` 和 `uv.lock`）。
- 采样用 M0.5 的 `plan_blocks` 与 `iter_block_samples`（4 个 worker），输入格式不变：每块 65³ 个 float32，全局整数索引乘 h 得坐标，小于 0 为内部。
- 下文命令里的 `PY` 指 `.venv/bin/python`（等价于 `uv run --frozen python`）。重型命令都在 `mkdir .scratch/heavy.lock` 成功后运行，结束后删除；晶格块还在 6 GB 的 `RssWatchdog` 下运行，并外加一个进程外的 RSS 守卫（`guarded.py`，原因见第 6 节）。

晶格块的栅格范围是 82 × 82 × 42 mm，得到 6 × 6 × 3 = 108 个块，全部被细采样（没有可跳过的块），共 29,659,500 个采样值（约 1600 万体素对应盒内体积，加上外扩一圈和块的共享面）。

- 解析球回调（不经块数组插值）：edge 1.0 → −0.069%（26,952 个三角形），edge 0.5 → −0.017%（108,792 个三角形）。块数组插值（三线性）使误差大约翻倍，仍远小于 M0.6 要求的 1%。
- 晶格块在其他 edge 下：0.30 → 5,295,736 个三角形、体积 45,982.8（−0.99%）；0.50 → 1,906,164 个三角形、体积 45,527.9（−1.96%）。欧拉示性数都是 −2774。
- 晶格块用图内核直接回调（不经块数组，约 3.2 µs/次）：7,794,272 个三角形、体积 46,331.6（−0.23%）、欧拉示性数 −2774。块数组路径的 −0.89% 主要来自三线性插值在细杆和节点处的误差。
- 采样值恰为 0：在盒 [10, 20]³ 上，`level_set` 有 602 次回调返回精确的 0.0，结果仍闭合、无退化三角形，体积 1000.0（`b_zero.py`）。

同一脚本前一次运行里，纯 Python 解析球是 0.638 µs，`Program.eval` 是 2.836 µs；Python 回调的开销在两次运行之间波动约 40%，numba 回调的更稳（0.152 / 0.154 µs）。晶格图内核每次一个点是 3.25 µs，批量求值是 0.652 µs/点；按 edge 0.25 约 3443 万次回调估算，逐点回调需要 1.9 分钟，批量只需 22 秒。实际跑一遍晶格块、回调直接用图内核，`level_set` 耗时 127 s。

| 0.25 mm | 916,482 个三角形（参照 437,160），盖子 476,808；重复有向边 716,064；不闭合 | 437,160 个三角形全部与参照逐位相同；规范化 sha256 相同 |

归属规则：三角形字典序最小的顶点落在哪个盒的核心区，就归哪个盒。实测只显示结果：体素 1.0 和 0.25 mm 时逐位一致，0.3 mm 时顶点最多差 3.2e-14 mm。推测原因是 manifold3d 从每次调用的包围盒最小角起、按固定间距生成网格点（回调收到的坐标就是这样排列的），体素是二进制可精确表示的数时没有舍入，否则不同包围盒的舍入不同；没有读它的源码确认。

### B 的确定性

规范化 = 顶点按坐标字典序、三角形（旋转到最小顶点编号开头，保持取向）按顶点编号排序。TBB 线程数用 `onecpu.c` 生成的 DYLD 注入库控制（manifold3d 的 macOS wheel 静态链接 TBB，`TBB_NUM_THREADS` 不起作用；用 `tbb_threads_probe.py` 实测，cpu/wall 默认 9.56，`TBB_NUM_THREADS=1` 仍是 9.49，注入 1 / 2 / 4 个 CPU 后是 1.00 / 1.99 / 3.95）。

| 形状 | 运行 | 结果 |
|---|---|---|
| 球 (edge 1.0) | 默认 ×2，TBB 1 / 2 / 4 线程 | 5 次规范化 sha256 全部是 286bb41b…，原始输出顺序的哈希也全部相同 |
| 胶囊 (edge 1.0) | 同上 | 5 次全部是 a3752f4c…，原始顺序哈希也全部相同 |
| 晶格 (edge 0.25) | 默认 ×2，TBB 1 / 4 线程 | 4 次规范化 sha256 全部是 b9e945f8…，原始顺序哈希也全部相同 |

注意这是同一台机器、同一 wheel 下的结果。`level_set` 的回调本身是串行的，所以这些测试没法证明库内部的并行阶段在别的核数下一定一致，只能说在 1、2、4、10 个线程这几种配置下一致。

### A. OpenVDB：安装

OpenVDB 在 PyPI 上没有可用的 Python wheel：

```
$ uv run --no-project --python 3.11 --with openvdb python -c "import openvdb"
error: No solution found when resolving `--with` dependencies
  cause: Because openvdb was not found in the package registry and you require openvdb, we can conclude that your requirements are unsatisfiable.

$ uv run --no-project --python 3.11 --with pyopenvdb python -c "import pyopenvdb"
error: No solution found when resolving `--with` dependencies
  cause: Because all versions of pyopenvdb have no wheels with a matching Python ABI tag (e.g., `cp311`) and you require pyopenvdb, we can conclude that your requirements are unsatisfiable.
```

- `https://pypi.org/pypi/openvdb/json` 返回 404。PyPI 全量项目列表里与 openvdb 有关的只有 `pyopenvdb`（0.1.0–0.1.4，只发布了一个 `cp37-none-any` 轮子）和 `pyopenvdb-3.8`（0.1.5，只有 `cp38-none-any`），都装不到 Python 3.11；`vdbfusion` 是 TSDF 融合库，只有 cp310 及更早的 Linux x86_64 wheel，也不暴露 `volumeToMesh`。
- Linux x86_64 同样不行：`uv pip install --dry-run --python-version 3.11 --python-platform x86_64-unknown-linux-gnu openvdb` 与 `pyopenvdb` 报相同的错误。
- Homebrew 有 C++ 库的 formula（`brew info openvdb`：stable 13.1.0，License: MPL-2.0），本次没有安装，也不属于 `uv` 安装。
- 按规则记为 **不通过：安装**。其余 6 项没有评估，表里不写任何关于 OpenVDB 性能或行为的数字。

## 对 M0.6 的影响

1. **自写 numba Marching Cubes 为准**，M0.6 的任务卡不变（O·xhigh）。ADR 0005 里关于块划分、跳块、全局整数坐标、按边编号焊接的规则全部保留。
2. **Marching Cubes 的计算量不是瓶颈**：scikit-image 参照在 108 块晶格上 0.448 s（单线程，未焊接），而 M0.5 采样要 5.9–9.1 s。M0.6 的难点在焊接和确定性，不在速度。
3. **RSS 看门狗会被饿死**：`level_set` 期间如果回调是 numba 函数，Python 线程完全得不到 GIL。`b_gil_probe.py` 实测，一次 6.83 s 的调用里一个每 50 ms 醒一次的线程只醒了 1 次（最长间隔 6.83 s）；回调是纯 Python 函数时能醒，但有间隔（1.56 s 里醒 21 次，最长间隔 0.38 s）。后果：这类调用里 `RssWatchdog` 看不到内存增长，限值失效（鞋盒 0.25 mm 那次，看门狗记录的峰值只有 240 MB，真实峰值 4.28 GB）。M0.6 的要求：自写 numba 内核保持 `nogil=True`（`graph/kernels.py` 已经这样做）；任何会长时间持有 GIL 的扩展调用（见下一条）都要在它前面做内存预估，或者放进 worker 进程。
4. **用 manifold3d 校验焊接后的网格是可行的，但要注意占用**：对规范化后的网格调用 `Manifold(Mesh64(...))`，5,295,736 个三角形用 1.03 s，RSS 从 340 MB 增到 2,654 MB（约 440 字节/三角形），期间同样持有 GIL（1.03 s 里线程只醒了 2 次，最长间隔 0.99 s）；1,906,164 个三角形是 0.28 s、峰值 1,014 MB。晶格块在 0.25 mm 下约 3.83 M 个三角形，按线性外推约 0.75 s、RSS 增量约 1.7 GB（外推，未测）。
5. **晶格块可作为 M0.6 的额外对照**：欧拉示性数 −2774（亏格 1388）在 manifold3d 的 edge 0.25 / 0.30 / 0.50 和图内核回调下都相同，体积参照 46,440 mm³（中点积分，收敛到约 0.02%）。Marching Cubes 在歧义格上的拓扑可能与 manifold3d 不同，所以示性数只作交叉检查，不作硬性验收。
6. **零值问题 manifold3d 没有遇到，但与 M0.6 无关**：“0 按外部处理”和焊接后按坐标再合并一次、删退化三角形的规则仍由 M0.6 自己实现和验证。
7. **线程数控制**：manifold3d 的 macOS wheel 静态链接 TBB，没有 Python API 和环境变量能改线程数。`spikes/m0_6a/onecpu.c` 的 DYLD 注入库可以让 TBB 只看到 N 个 CPU，M0.6 的校验步骤若要验证“线程数不影响结果”，可以直接复用。

## 本次没有做的事

- OpenVDB 完全没有评估（装不上）。若以后要评估，需要从源码编译 C++ 库和 Python 绑定，或改用 conda 环境，都不属于 `uv` 直接安装，按规则不在 M0 范围内。
- 没有实现自写 numba Marching Cubes，所以没有它的焊接耗时和内存数据，只有 scikit-image 的速度参照。
- 没有用真实鞋楦；晶格块是解析形状，没有鞋楦采样场的窄带和粗栅格。
- 晶格块的非流形顶点检查（单个顶点的邻接三角形是否构成一个扇）没有对 8.1 M 个三角形做；闭合与取向一致、零面积三角形、欧拉示性数都做了，并有 `Manifold.status()` = NoError 作为库自己的校验。
- 机器上还有其他进程在跑，耗时和 RSS 有波动；表里直接给出了多次运行的范围，而不是挑一次。
